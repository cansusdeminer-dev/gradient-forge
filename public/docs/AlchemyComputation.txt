Alchemy Studio
A Unified Procedural SFX Engine for Hyperreal “Anything” (Whitepaper / Design Spec)
Abstract

Alchemy Studio is a browser-first, node-graph-based procedural engine that can synthesize any visually plausible object or phenomenon for SFX—clouds, trees, rocks, gradients, liquids, fabrics, characters, and animated systems—by compiling typed graphs into fields, geometry, materials, and motion. The engine is designed as a universal artifact compiler: you author a graph; the system evaluates, caches, simulates, renders, and exports results at cinematic fidelity, with deterministic reproducibility and deep introspection.

The core thesis is simple:

For SFX realism, “anything” is reachable via the right combination of
(1) representation, (2) degrees of freedom, and (3) control tooling.

Alchemy Studio is the control tooling.

1) The Design Target: “Any Object” in the Visual Domain
1.1 What “ANY object” means here

Not molecular truth. Perceptual truth: correct enough that the eye, camera, and audience buy it.

This implies:

Multi-scale structure (macro silhouette → meso forms → micro detail)

Physically plausible light response (surface + volume)

Plausible motion (rigging, constraints, dynamics, secondary motion)

Consistency under camera changes (parallax, shadows, scattering, specular behavior)

Authorability (you can actually steer it)

1.2 The four invariants of SFX objects

Everything in your list decomposes into four universal outputs:

Shape: where “stuff” exists

Surface: how the boundary reflects/refracts light

Volume: how light interacts inside (fog, skin, clouds, smoke, SSS)

Motion: time evolution (rigs, sims, procedural animation)

Alchemy Studio treats those as first-class outputs.

2) Baseline Architecture (What You Already Have)

Your current draft (GradientForge-style) is a correct seed: a node graph evaluated in topological order. The baseline pattern is:

Nodes carry { moduleType, params }

A module provides:

inputs[], outputs[]

compute(w, h, params, inputs) -> ImageData

Graph execution:

Build input map from edges

Topological sort (Kahn-style)

Evaluate nodes in order

Cache results per node

That’s the right skeleton. The “alchemy leap” is not replacing it—it’s generalizing it.

3) The Alchemy Kernel (Core Engine Concept)
3.1 The universal internal language: Typed Resources

Replace “everything is ImageData” with “everything is a resource with semantics.”

Resource types (minimal power set):

Field2D: scalar or RGBA function over (x,y)

Field3D: scalar/vector function over (x,y,z)

SDF3D: special Field3D where value is signed distance to surface

Volume: sparse/dense 3D texture + metadata (units, bounds, channels)

Mesh: triangles (or quads) + attributes (normals, tangents, UVs, vertex colors)

Curve/Graph: splines, growth skeletons, guide curves

Material: layered BSDF parameters, texture slots, and procedural closures

Rig: skeleton, constraints, skin weights, IK/FK controls

Motion: animation clips, curves, procedural signals

SimState: persistent state for fluid/cloth/particles/soft bodies

Port typing rule: edges must connect compatible types or pass through explicit converters.

3.2 The compilation model: Graph → IR → Backends

Don’t “just evaluate nodes.” Compile.

Graph IR (Intermediate Representation)
A normalized, backend-agnostic program:

validated types

resolved dependencies

constant-folded parameters

partitioned into compute stages (CPU/WebGPU/shader/renderer)

Backend compilation
Each stage becomes:

CPU kernels (reference)

WebGPU compute pipelines (fast)

shader graphs (viewport)

offline render passes (cinematic)

This is how you get a single authoring model with multiple execution targets.

4) Execution Semantics: Time, State, Determinism
4.1 Three execution modes

Static Evaluation (still image / single frame)

Animated Evaluation (time as input)

Simulated Evaluation (time + persistent state)

4.2 Pure vs Stateful nodes

Pure nodes: out = f(in, params, time)
Cacheable, parallelizable, deterministic.

Stateful nodes:
state_out, out = g(in, params, time, dt, state_in)
Ordered, ticked, optionally baked.

This avoids feedback-loop chaos while still supporting “living” systems.

4.3 Determinism (non-negotiable for SFX)

Alchemy Studio must support:

stable seeds derived from graph hashes

versioned node signatures

reproducible bakes (frame N always matches)

This is what turns procedural into pipeline-grade.

5) Data Structures for “Anything”
5.1 Fields as functions, not just textures

A field can be:

sampled procedurally (value = noise(x,y,z))

stored as textures/volumes (dense)

stored as tiles/chunks (sparse)

hybrid (procedural at low frequency + stored residual details)

5.2 Sparse volumes (clouds, smoke, fog, SSS maps)

You want OpenVDB-like behavior conceptually:

tiled 3D grids

region-of-interest evaluation

mipmapped / multires volumes

streaming updates

5.3 Mesh + field coupling

Power move: treat meshes as views of fields.

SDF → mesh extraction (marching cubes / dual contouring)

mesh → field baking (AO, curvature, thickness, distance-to-feature)

field-driven displacement and fracture masks

This makes rocks/trees/skin/wetness all feel coherent.

6) Node Taxonomy (Spell Schools)
6.1 Generators (create signals)

Noise families: value, gradient, simplex, cellular, ridged, domain-warped

Analytic shapes: gradients, ramps, splines, distance fields

Pattern grammars: L-systems, space colonization, tilings, lattices

3D base volumes: stratified density, turbulence stacks

6.2 Modifiers (transform signals)

Domain transforms: warp, twist, bend, flow-map, curl noise advection

Frequency shaping: octave stacks, bandpass, histogram remap

Morphology: erosion/dilation (2D/3D), ridge extraction, crack growth

Filters: blur, sharpen, edge detect, anisotropic smoothing

6.3 Geometry (SDF / implicit modeling)

Primitives: sphere/box/capsule/torus/superquadrics

CSG: union/subtract/intersect

Smooth CSG (blends): smooth unions that preserve curvature continuity

Feature ops: bevel/fillet approximation, chamfer, edge rounding masks

Detail ops: displacement with curvature-aware amplitude

6.4 Volume / Atmospherics

Density authoring: base shapes + erosion + detail noise + humidity/temperature fields

Lighting fields: self-shadow approximations, light transport caches

Advection: vector-field-driven motion

Phase functions + multi-scatter approximations for cinematic results

6.5 Materials (appearance truth)

Layer stacks: base → coating → dirt → wetness → frost → moss

Procedural masks: curvature, AO, thickness, slope, cavity, flow accumulation

Microstructure: normal synthesis, microfacet parameter fields

Spectral-ish hacks: thin-film interference, iridescence closures

6.6 Motion / Rigging

Skeleton generation from structure graphs (trees, creatures, props)

Constraints: hinge, ball joint, limits, springs

IK solvers: CCD / FABRIK style

Skinning: weight generation from distance fields / heat diffusion approximations

Animation: curve graph, noise-driven motion, clip blending, retargeting

6.7 Simulation nodes (stateful)

Particles: SPH-like for goo; PBD-like for stable cloth/ropes

Vegetation wind: field-driven deformation + inertia + phase offsets

Simple fluids: shallow-water + spray particles + foam maps

Volumes: advection + buoyancy + dissipation (smoke-lite)

Fracture-lite: stress fields → crack masks → mesh splitting (stylized to realistic)

6.8 Extract / Export

Field2D → textures (PBR set baking)

SDF3D → mesh extraction + remesh + UV (basic first, robust later)

Mesh + Material → glTF/GLB export

Volume → 3D texture cache / flipbook impostors / raymarch assets

Animation → clips + curves + baked sim caches

7) The “Alchemy” Parameter System (How You Avoid Knob Hell)
7.1 Parameters as a constrained space

A raw slider per variable is death. Instead:

Parameter groups with meaning (Weathering, Grain, Age, Moisture)

Macro controls that drive multiple internal params via curves

Constraints (ranges, correlations, monotonic relationships)

Units & semantics (meters vs normalized, density vs opacity)

7.2 Parameter wiring and expressions

Every parameter can optionally be driven by:

a constant

an animation curve

another field sampled at a point

a procedural signal node

a learned prior node (optional)

This turns the graph into a real “control lattice.”

7.3 Variation rigs (deterministic generative families)

A “variant” is not random chaos; it’s controlled diversity.

Seeded randomness per node and per subgraph

Distributions (normal/lognormal) not uniform noise

Bounds + artistic constraints

“Family sliders” (style DNA controls)

This is how you generate 500 unique rocks that all belong to the same world.

Realtime viewport: raster + hacks (but very good hacks)

8.2 Material truth checklist (for “it looks real”)

8.3 Volume truth checklist

temporal stability (no shimmering during motion)

4) “Edit the Preview” Without Breaking the Graph
Direct Manipulation as Graph Edits (Bidirectional Editing)

This is the killer feature: you edit in the viewport and the system updates the graph in a principled way.

4.1 The rule: edits become operations, not raw mutations

When the user drags/paints/sculpts, you do not rewrite a mesh directly (unless explicitly in destructive mode). You insert a node:

“Translate this feature”

“Adjust this gradient stop”

“Paint a mask”

“Sculpt a displacement delta”

“Move these control points”

“Add a fillet here”

“Increase roughness along edges”

4.2 Three categories of viewport edits
A) Parameter edits (best case)

You interact with the object and it maps cleanly to existing params
Example: drag a cylinder radius handle → updates radius.

B) Constraint edits (CAD case)

You drag something and constraints update dimensions/relations
Example: move a sketch point → solver updates other points.

C) Residual edits (the “this doesn’t fit params” case)

When the current paramization can’t represent the edit cleanly, add a Residual Layer Node:

Stores a delta field / displacement / corrective shape

Can be painted, sculpted, filtered, blended

Remains deterministic and replayable

This is how you avoid the false binary of “procedural vs manual.”

Alchemy Studio — Part II
Boolean + CAD + Direct Manipulation + “Hyper-Graph” Editing, pushed to the wall

You said proceed, so we’re going to keep sharpening this into a full-stack engine spec: not just “nodes,” but the geometry kernel, CAD feature history, viewport editing, painting/sculpting layers, and the compiler/runtime that makes it all coherent.

1) The Unifying Philosophy: Everything Is an Operation, Everything Is a Layer

Alchemy Studio is a non-destructive operation system.

1.1 The three editing strata

Procedural strata (generators, rules, functions)

Feature strata (CAD/history-tree ops: sketches, fillets, drafts)

Residual strata (manual edits captured as deltas: paint/sculpt/correctives)

All three are equal citizens in the graph.

1.2 The “Edit Canon”

When the user edits in the viewport, the engine chooses (in order):

(A) Param edit → update existing params (best)
(B) Feature edit → insert/update a CAD-feature node (great)
(C) Residual edit → add a delta layer node (always works)

This is how you never get stuck.

2) Geometry Kernel: How You Support CAD and SDF and Mesh Without Dying

You want: booleans, CAD-ish exact tools, sculpt, displacement, warps, and exports. The only sane way is multi-representation with a canonical source.

2.1 Canonical-by-domain policy

SDF-first for: procedural alchemy, topology changes, sculpt, blends, erosion, destruction

B-Rep-first “CAD islands” for: sketches, precise dimensions, feature stacks, mechanical-ish assets

Mesh-first for: imported assets, scanned assets, high-detail sculpt outputs, rendering/UV workflows

Key rule

A single object can contain multiple subdomains (e.g., CAD core + SDF weathering + mesh detailing), but at any evaluation moment, each region has a canonical representation and the others are derived views.

2.2 Representation bridges (the actual alchemy)

These are mandatory nodes/services:

B-Rep → SDF (Exact-ish to sculptable)

Sample distance to trimmed surfaces with acceleration (BVH)

Use adaptive sampling + error bounds (tight near features)

Produce multi-res distance field tiles

SDF → Mesh (Viewport + Bake)

Marching Cubes (fast baseline)

Dual Contouring / Hermite data (feature preservation)

“Sharp feature” reconstruction using gradient + crease detection

Mesh → SDF (Make any imported object boolean-friendly)

Fast winding number / ray parity

Signed distance via closest point + inside test

Store as sparse tiles (clipmap)

Mesh ↔ B-Rep (Mostly optional; hard)

Keep this limited: allow sketch + feature to operate on B-Rep regions, and treat mesh as export/viewport.

If you try full mesh→NURBS reverse engineering, you’ll invent a new kind of suffering.

3) Boolean Operations: The Full Boolean Kernel

Booleans are not “Union/Subtract.” They are a domain with policies.

3.1 Boolean modes (choose per situation)
Mode 1: SDF Boolean (default, robust, sculptable)

Union: min(d1, d2)

Intersect: max(d1, d2)

Subtract: max(d1, -d2)

Mode 2: Smooth / Blend Boolean (cinematic, organic)

Replace min with smooth-min variants:

Polynomial smooth-min

LogSumExp smooth-min

R-function blends

Blend radius can be a field (paintable bevels)

Mode 3: Feature-preserving Boolean (hard edges stay hard)

Core idea: blend only where allowed, preserve creases by masks:

Compute creaseMask = f(|∇d|, curvature, user paint, angle thresholds)

Blend factor becomes: k(x)=k0 * (1-creaseMask)

Mode 4: CAD Boolean (for B-Rep islands)

Uses tolerances, healing, edge merging

Produces exact-ish topology for dimensioned parts

Mode 5: Mesh Boolean Fallback

Honestly: best practice is mesh → SDF → boolean → mesh, unless you need exact face topology.

3.2 Boolean material rules (the realism kicker)

When you union rock + moss + wetness, “who wins” can’t be arbitrary.

Define Material Compositing Policies:

Winner-takes-all by priority layer

Blend by distance (within bevel region)

Blend by mask (painted or procedural)

Physically inspired (e.g., wetness overrides roughness + darkens albedo)

Booleans should output:

geometry (SDF or mesh)

material layers (weights)

seam masks (useful for grime accumulation)

curvature/edge features (for wear)

4) CAD as Nodes: Feature Graph = History Tree = Subgraph

A CAD system is a constrained feature history. You already have a graph. Great. You just need a CAD dialect.

4.1 Sketch nodes

Sketches are themselves graphs:

Entities: points, lines, arcs, splines

Constraints: coincident, parallel, tangent, equal, symmetry, distance, angle, radius

Dimensions are parameters that can be:

keyed on the timeline

driven by procedural signals

The Alchemy Engine

Abstract

We propose an interactive engine for constructing hyper-realistic digital objects and phenomena (e.g., clouds, oceans, trees, rocks, gradients, fabrics, characters with rigging/animation) through a typed, layered hypergraph of procedural and parametric operators. The engine emphasizes:

Universal composability: everything is a graph (shape, shader, simulation, animation).

Hybrid representations: SDF/fields + meshes + volumes + textures + rigs, interoperable.

1) Core thesis: “Anything” is possible (in the perceptual sense)

# C) Representation Bridges in the Browser: Make Them Incremental, Tiled, and Multi-LOD

This is the engineering bottleneck Gemini flagged, and it’s real.

The rule for survival is:

> No “full recompute” conversions during interaction.
> Everything is **tile-based** and **LOD-first**.

### C.1 Canonical SDF + sparse clipmaps (interactive core)

For SDF-first workflows:

* Store SDF in a **sparse tile set** (clipmap / mip hierarchy).
* Each brush stroke marks only affected tiles **dirty**.
* GPU compute updates only those tiles.

### C.2 Meshing must be patch-based, not global

When you need SDF → mesh:

* Extract only the dirty region first (low-res)
* Then refine (higher-res tiles) when idle / on mouse-up

Interaction strategy:

* **While dragging/painting:** show **raymarched SDF preview** or coarse mesh patches
* **On release:** refine mesh + normals + curvature caches
* **On bake:** full quality extraction and remesh

This prevents browser lock-ups and keeps the UI “alive.”

### C.3 “Live stroke” caching policy (explicit)

Define a standard pipeline for brush edits:

1. Apply stroke → generate a **delta field** (low-res tiles)
2. Compose delta into canonical field (still low-res)
3. Render preview (raymarch or coarse mesh) immediately
4. Kick background refinement jobs:

   * higher-res tiles
   * curvature/AO/thickness maps
   * better normals / feature lines

Key: the UI always has *something* to show in <1 frame, even if it’s coarse.

### C.4 CAD islands: don’t bridge unless needed

For B-Rep “CAD islands”:

* Keep them B-Rep while doing constraint edits / precise features
* Only bake/bridge to SDF when:

  * you enter sculpt mode,
  * you do blend booleans,
  * you need volumetric effects,
  * or you’re baking/exporting.

This prevents pointless conversion churn.

# D) Residual Edit Threshold: Make the Interpretation Obvious and User-Controllable

This is the UX landmine: if the system silently chooses “residual,” users will feel betrayed.

### D.1 Every viewport edit must emit an “Edit Interpretation HUD”

At the cursor, for ~1 second, show:

* **Interpreted as:** `Macro Param` / `Constraint Solve` / `Residual Layer`
* **Affected scope:** `Global / Regional / Local`
* **Revert target:** clickable (jumps to the node/layer created/edited)

Example microcopy:

* “Edited: **Erosion.Amount** (macro)”
* “Solved: **Sketch constraint** (dimension update)”
* “Created: **DeltaSDF Layer** (local sculpt)”

No ambiguity. Ever.

### D.2 Offer a one-click override *immediately*

Right in that HUD:

* “Prefer **Macro**” (try to fit edit into existing params)
* “Prefer **Residual**” (force local layer)
* “Always do this for this tool”

This makes the edit ladder *explicit* rather than “mystical.”

### D.3 Residual layers need their own “lane” in the timeline/layer stack

Residual edits are not second-class.
They appear as:

* a named layer
* with masks
* with blend mode
* with reorder
* with ability to “generalize”

### D.4 “Generalize residual” is the bridge back to procedural purity

A super important concept:

> A residual layer can be *promoted* into parameters later.

Mechanisms:

* Fit a simpler param model to the residual (curve/profile/noise parameters)
* Or use your inverse-design solver to approximate the residual within constraints

This converts “manual hacks” into reusable procedural controls when desired.

Aether Alchemy Engine
A unified authoring language for “digital matter” (hyperreal visuals, SFX, CAD-ish geometry, simulation, rigging, animation) in the browser

You’re not describing “a node editor.” You’re describing a compiler + runtime for a new kind of artifact: a deterministic, typed, serializable “matter program” that can be edited visually, manually, and inversely—without ever breaking reproducibility.

Below is a paper-style spec that pushes the idea to the edge of sanity (in the fun way): multi-representation geometry, non-destructive viewport edits that become nodes, CAD booleans, sculpt/paint-as-graph, simulation coupling, rigging/animation, plus the UI doctrine you’re building around (visual instruments, ROM zones, connected editors, capsules).

Abstract

We propose Aether Alchemy, a browser-first engine for constructing hyperreal “digital objects” (materials, meshes, SDF volumes, clouds, fluids, characters, CAD-like solids, animated rigs) via a typed hypergraph that compiles into multiple execution backends (GLSL/WebGPU shaders, SDF evaluators, meshing pipelines, simulation compute graphs, rig/animation solvers).

The core thesis:

Everything is an operation. Sliders are a failure mode; visual instruments are the default control surface.

Everything is reproducible. Viewport edits are not destructive states—they compile into graph nodes that capture intent.

Everything is multi-representation. SDF-first for robustness + booleans; B-Rep “CAD islands” for constraints; mesh extraction as a view/export target.

Everything is incremental. Real-time editing requires a dirty-propagation system, caching, and LOD across representations.

Everything can be inverse-designed. Intent nodes let artists specify outcomes; solvers tune parameters under constraints.

3) The Multi-Representation Geometry Kernel
3.1 Canonical geometry: SDF-first (robust booleans + blending)

SDF is the canonical procedural geometry because:

booleans are stable (min/max blends, smooth unions)

topology changes don’t explode

LOD is natural (sample at different resolution)

it composes with volumetrics (cloud density, fog, pyro fields)

Core operations:

primitives: sphere, box, capsule, superquadric, cones, rounded variants

transforms: warp, bend, twist, lattice, noise displacement

booleans: union/intersection/difference

smooth ops: smooth union, chamfer union, fillet-like blends

morphological: dilate/erode/open/close (extremely powerful for “realism”)

3.2 B-Rep “CAD islands” (constraints + sketches + surfaces)

B-Rep exists for:

sketches (2D constraints: parallel, perpendicular, equal, tangent)

param surfaces (NURBS-ish)

dimension-driven edits (actual CAD muscle)

But B-Rep is not forced everywhere. It’s an island representation that can be:

converted to SDF (distance evaluation / rasterization / analytic distance where possible)

meshed directly (for crisp hard-surface exports)

3.3 Mesh as a view/export product, not the source of truth

Meshes are:

extracted from SDF (dual contouring / adaptive marching cubes)

produced by B-Rep tesselation

modified by mesh operators (decimate, subdiv, remesh, UV unwrap)
…but the engine treats mesh editing as either:

a derived layer (non-destructive mesh modifiers), or

a residual (delta field / displacement / mesh delta) that still lives in the graph.

3.4 Representation bridges (the hard part)

Bridges must be explicit nodes with caching + LOD:

BRepToSDFNode (with resolution, narrow-band distance, adaptive sampling)

SDFToMeshNode (LOD, adaptive extraction, feature preservation)

MeshToSDFNode (voxelization + fast sweeping / jump flooding)

FieldToMeshNode (iso-surfacing)

SDFToVolumeNode (density mapping, fog/cloud conversion)

Each bridge:

advertises cost

supports incremental recompute (tiles/chunks)

can degrade gracefully during interaction (coarse preview), refine on idle.

4) Viewport Editing That Compiles Into Nodes (the killer feature)
4.1 The Edit Ladder (how gestures become non-destructive intent)

When the user drags/paints/sculpts in the viewport, the system tries, in order:

Parameter solve (macro edit)
“This drag corresponds to a known parameter.”
Example: dragging a wave crest adjusts amplitude + steepness through a WaveProfile instrument.

Constraint solve (structured edit)
“This drag corresponds to a CAD constraint / rig constraint / layout constraint.”
Example: moving a hole keeps concentricity, maintains dimension constraints.

Localized procedural insertion (intent node)
“I can express this edit by inserting a node: taper, bevel, warp, mask, sculpt brush node.”

Residual (delta layer)
“No clean param explains this; store it as a delta.”
Examples:

DeltaSDFNode (localized signed distance edits)

DeltaDisplacementNode (vector displacement field)

PaintMaskNode (painted scalar field that modulates downstream ops)

MeshDeltaNode (mesh-space deltas, last resort)

This ladder preserves the user’s thesis: manual edits are not destructive mode-switches—they’re new nodes.

Meshing backend: SDF/B-Rep → mesh extraction/tessellation

Simulation backend: cloth/fluid/rigid compute graphs (WebGPU compute)

Rig/animation backend: constraints + IK + ROM zones + blendspaces

5.2 Candidate generation

5.3 Scoring function (the honest math)

A good scoring function should reward:

closeness to user intent

minimal complexity

high generality / reusability

ROM safety (avoid unstable zones)

low runtime cost

Example:

score = 
  w_fit     * fitError(intent, predicted) +
  w_cost    * estimatedRuntimeCost(candidate) +
  w_scope   * scopePenalty(candidate, intent.locality) +
  w_rom     * romPenalty(affectedParams) +
  w_entropy * graphComplexityPenalty(candidate) -
  w_reuse   * reusabilityBonus(candidate);

Decision policy:

Choose best score if margin is clear

If ambiguous: obey per-tool policy (preferMacro, preferResidual, askWhenAmbiguous)

5.4 Output: the Edit Interpretation HUD payload

8) Lowering Rules (How nodes compile)

This is the “compiler constitution.”

8.1 Shader-lowered nodes

When: pure functions, cheap per-sample evaluation
Examples: SDF primitives/booleans/warps, PBR shading, small math nodes

Pros: instant updates via uniforms
Cons: expensive if you sample too many times (raymarch), not good for big filters

8.2 Compute-lowered nodes

When: operations over spatial grids/tiles/bricks
Examples: paint masks, blur, curvature/cavity caches, advect, SDF→mesh extraction

Pros: incremental, tiled, cacheable
Cons: more infrastructure (buffers, bind groups, scheduling)

8.3 CPU/WASM-lowered nodes

When: iterative solvers, graph optimization passes, constraint solves
Examples: CMA-ES, Nelder-Mead, sketch constraint solve (CAD), rig solve if needed

Rule: CPU jobs must be time-sliced to preserve interactivity (cooperative scheduling).

9) Preview vs Interactive vs Final (Quality contract)

Every node declares a preview degrade strategy:

Drop high-frequency octaves in noise

Lower brick/voxel resolution

Raymarch fewer steps

Mesh extraction coarse

Skip curvature/cavity recompute mid-stroke (use stale cache)

Defer expensive filters until mouse-up

This is how browser-first stays “alive.”

What you do next with this (the compiler-brain part)

Treat nodes[] as the registry: the editor can only instantiate ops present here.

When you build your runtime, each opId maps to an implementation:

lowering: "shader" → WGSL function snippet + param uniforms

lowering: "compute" → compute pipeline + tile/brick dispatch strategy

granularity tells the scheduler what invalidation to track (global, tile2d, brick3d, mesh_patches)

The UI reads params.*.rom and draws comfort/strain/danger bands automatically.

# Terrain Brush Encyclopedia (Draft)

**Project:** GPT5.2WORLD  
**Purpose:** A practical, “first principles” reference for how GPT5.2WORLD’s terrain editing tools emulate real-world mountain morphology while staying deterministic and interactive.

## 1) The promise: “paint geology, not pixels”

When a user draws a mountain range, they’re rarely trying to “add random height”. They’re trying to create:

- A **tectonic-scale structure** (where the high ground is and why)
- A believable **drainage structure** (where water *wants* to go)
- A believable **texture** (ridges, scarps, talus aprons, fans)
- Coherent downstream consequences: slope, rivers, wetness, ice potential, etc.

GPT5.2WORLD’s approach is to treat editing as **changing causal fields** (elevation first, then derived layers), rather than painting a cosmetic overlay.

Key implementation files:

- Terrain brush (point tool): `src/engine/edit/terrainBrush.ts`
- River polyline tool: `src/engine/edit/polylineTools.ts` (`applyRiverPolyline`)
- Mountain range polyline tool: `src/engine/edit/polylineTools.ts` (`applyRidgePolyline`)
- Local erosion helpers (thermal + drainage incision): `src/engine/edit/localErosion.ts`
- Recompute pipeline after edits: `src/engine/world/worldModel.ts` (`rebuildDerivedFieldsV1`)

## 2) Field model and units (what we’re actually editing)

### 2.1 Normalized elevation

- `HEIGHT` is stored as a normalized float in `[0..1]`.
- `seaLevel` is also in `[0..1]`.
- “Land elevation” is `max(0, HEIGHT - seaLevel)`; many processes depend on it.

This is not real meters yet. The engine’s strategy is:

1. Make the *geometry* believable in a normalized space.
2. Derive stable indices (slope, flow accumulation, wetness, etc.).
3. If needed later, map to physical meters via a calibrated “vertical scale” layer.

### 2.2 The derived atlas (why edits feel “alive”)

After a height edit, GPT5.2WORLD recomputes derived layers:

- **Geomorphology proxies**: slope, curvature-ish signals, roughness
- **Hydrology proxies**: D8 flow direction + accumulation, river mask, wetness
- **Coupled systems (MVP baseline)**: tectonics fields, climate proxies, ocean baseline, cryosphere, stratigraphy, marine ecosystem

These are calculated in:

- `src/engine/atlas/FieldAtlasV1.ts`
- `src/engine/world/worldModel.ts`

## 3) Mountain genesis: the “big 3” families

Real mountains are not random. Their *macro* form is strongly constrained by tectonics and volcanism. The terrain tools mirror this by having **mountain archetypes**.

### 3.1 Fold-thrust belts (convergent orogeny)

**Real-world signature**

- Broad, continuous ranges (Himalaya, Andes segments, Zagros)
- Parallel sub-ridges and fold trains
- Foreland basins adjacent to the belt
- Strong ridge/valley anisotropy (structure-controlled topography)

**What to emulate in a brush**

- A main ridge backbone
- Secondary, parallel ridges (lower amplitude)
- Gentle basin subsidence on the flanks to avoid “perfect walls”

### 3.2 Fault-block mountains (extension / rifting)

**Real-world signature**

- Asymmetric ranges: a sharp **fault scarp** on one side, a gentler back-slope on the other
- Adjacent subsiding basins (grabens / half-grabens)
- Long straight range fronts (in the simplest case)

**What to emulate in a brush**

- Strong, narrow uplift on one side of the line (scarp)
- Broader, weaker uplift on the opposite side (back-slope)
- Basin depression further outboard (down-dropped basin)

### 3.3 Volcanic arcs (subduction volcanism)

**Real-world signature**

- Chains of stratovolcanoes with spacing and variability
- Cones, calderas/craters, lava aprons
- Often co-located with uplifted arc/back-arc regions

**What to emulate in a brush**

- A line-guided cone “stamp” with spacing
- Crater depressions at cone summits
- Apron build-out around cones

### 3.4 Glaciated alpine terrain (process overprint)

**Real-world signature**

- Glacially widened valleys trending toward U-shapes
- Strong headwater dissection; dense ridge networks
- High relief often co-located with cold + wet conditions

**What to emulate in a brush**

- Start with an orogenic backbone (often fold-thrust-like macro relief)
- Add fluvial dissection to seed valley networks
- Apply a valley widening carve around channels in cold/high terrain

## 4) Surface processes: why mountains look “real” at human scale

Once a macro mountain exists, **surface processes** shape its micro/mid-scale realism:

### 4.1 Mass wasting (thermal / talus relaxation)

Steep slopes are unstable. Material moves downslope until the slope is near a stable “angle of repose”.

In an interactive tool, a fast approximation is **thermal erosion**:

- Identify cells that are much higher than their neighbors
- Move a small amount downslope if the local height difference exceeds a “talus” threshold

This creates:

- Talus aprons
- Rounded shoulders
- Reduced “blocky” artifacts from stamping

### 4.2 Fluvial incision (channels carve structure)

Most of the recognizable mountain texture comes from water:

- Headwaters incise rapidly
- Channels focus flow and create branching patterns
- Incision competes with deposition and slope diffusion

In interactive editing, a lightweight approximation is:

- Start many “droplets” near high ground
- Let each droplet walk downhill (steepest descent)
- Carve a small amount along the path (optionally deposit tiny amounts)

This produces:

- A drainage grain that immediately reads as “geomorphic”
- More believable ridge dissection and valley spacing

### 4.3 Glacial carving (current + future)

Glaciated alpine terrain has distinctive shapes:

- U-shaped valleys
- Cirques, horns, arêtes

GPT5.2WORLD includes a first, lightweight glacial proxy in the **Glaciated alpine** range type:

- Uses drainage incision hits as a proxy channel network
- Computes a local cold/high index from latitude + elevation
- Widens and deepens valleys around that network to bias shapes toward trough-like valleys

Longer-term plan (more physical) is:

- Compute a local “glacial potential” index (cold + high + wet)
- Where potential is high, widen valley floors and steepen sidewalls along major flows
- Add cirque excavation at headwalls

## 5) GPT5.2WORLD implementation: the current mountain range brush

The mountain range tool is polyline-based: you draw a backbone, the engine synthesizes a plausible range around it.

### 5.1 Range types (UI)

In the editor’s “Mountain range” polyline tool:

- **Fold-thrust**: ridge + subridges + subtle foreland basins
- **Fault-block**: asymmetric scarp + back-slope + basin
- **Volcanic arc**: ridge foundation + volcano cones with craters and aprons
- **Glaciated alpine**: fold-thrust-like macro relief + drainage incision + glacial valley widening proxy

### 5.2 Algorithm overview (`applyRidgePolyline`)

Code: `src/engine/edit/polylineTools.ts`

Pipeline:

1. **Resample the polyline** to ~1px spacing for consistent stamping.
2. For each sample:
   - Compute a **local tangent** (direction along the line)
   - Compute a **normal** (left/right side of the range)
3. Apply a **macro structure** based on `kind`:
   - Fold-thrust: main ridge + symmetric subridges + subtle flank basins
   - Fault-block: strong scarp uplift on one side, basin depression further out
   - Volcanic arc: periodic cones + crater depressions + apron deposition
4. Apply **thermal erosion** (fast talus relaxation) in a padded bounding box.
5. Optionally apply **drainage incision**:
   - Launch droplets from near the ridge line
   - Walk downhill by steepest descent
   - Carve a small amount per step

6. If **Glaciated alpine**:
   - Treat drainage paths as a channel network
   - Compute a cold/high potential index
   - Apply a widening carve around channels to bias valleys toward trough-like shapes

This order matters: macro first, then surface processes “explain” the detail.

### 5.3 Key parameters and how they map to geology

#### Radius (`radiusPx`)

- Larger radius → broader range footprint and wider deformation zone.

#### Strength (`heightGain`)

- Controls maximum uplift/relief contribution.
- Higher values create higher peaks, but also stronger incision if drainage carving is enabled.

#### Ruggedness (`ruggedness`)

- Controls micro-variability: ridged texture and end taper.
- Higher ruggedness also increases erosion amount to keep steep slopes from looking artificial.

#### Thermal relax (`thermalIters`) + talus (`talus`)

- More iterations → smoother, more “mass-wasted” slopes and talus aprons.
- Higher talus → less material moves (preserves sharper features).

#### Drainage droplets (`drainageDroplets`)

- More droplets → denser branching, stronger channel texture.
- Use sparingly on very high resolutions if you notice interaction lag.

## 6) “Magic” editing workflows (recommended)

### 6.1 Build a believable orogeny in minutes

1. Draw a **Fold-thrust** range to establish high ground.
2. Increase **ruggedness** until ridges start reading as “rocky”.
3. In “Erosion (advanced)”, keep **Carve drainage** on.
4. Draw a **River path** from mountains to the sea:
   - This helps enforce macro drainage intent (where the big rivers should be).
5. Use the point brush:
   - **Smooth** to remove accidental spikes
   - **Lower / River carve** to accentuate major valleys

### 6.2 Create Basin-and-Range style terrain

1. Draw several **Fault-block** polylines roughly parallel.
2. Keep radius moderate; use multiple passes rather than one giant stamp.
3. Use “River path” to connect basins to outlets (endorheic basins are also possible if you avoid outlets).

### 6.3 Volcanic island arc

1. Set range type to **Volcanic arc**.
2. Draw an arc-shaped polyline offshore.
3. Raise sea level slightly to emphasize islands, then lower it to expose shelves.

- Replaying the same edits yields the same world.
